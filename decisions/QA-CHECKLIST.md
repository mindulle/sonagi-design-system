# Sonagi 디자인 시스템 QA 체크리스트

이 문서는 ADR이 아니라 **재사용 절차서**입니다. 색상(0001)·타이포(0002)·Shadow(0003) 작업 중 실제로 놓칠 뻔했던 것들을 일반화해 정리했습니다. 새 토큰이나 컴포넌트를 결정/구현할 때마다 이 목록을 순서대로 대조하세요. 디자인 비전문가가 진행해도 전문가급 검증 수준을 유지하기 위한 안전장치입니다.

담당자(사람)는 매 단계 결과를 보고받고 최종 승인만 하면 되고, 각 항목의 실제 계산/검증은 에이전트가 수행합니다.

---

## A. 값을 "결정"할 때 (색상/타이포/spacing/shadow 등 토큰 레벨)

- [ ] **출처 확인**: 이 값이 어디서 왔는가? 기존 문서(DESIGN.md 등)에 있다고 그대로 믿지 말고, 실제로 근거(커밋 히스토리, 계산 방식)가 있는지 역추적한다. (색상 ADR 0001: 근거 없는 단일 커밋 발견 / 타이포 ADR 0002: Tailwind 기본값 복붙 발견)
- [ ] **수학적 파생 방식**: HSL의 임의 조정이 아니라, 지각적으로 균일한 공간(OKLCH)이나 고정 비율(모듈러 스케일) 등 재현 가능한 방법으로 도출했는가? hover/active 같은 파생값이 hue를 유지한 채 명도만 이동했는지 확인.
- [ ] **접근성(WCAG) 검증**: 실사용될 모든 fg/bg 조합의 대비를 계산했는가 (본문 4.5:1, UI/큰 텍스트 3:1, 비텍스트 UI 경계 3:1 — WCAG 1.4.11). 통과/실패 표를 남긴다.
- [ ] **지각적 구분(Delta E)**: 서로 다른 역할을 가진 인접 토큰들이 실제로 눈에 띄게 구분되는가(ΔE2000 기준 대략 2 미만=거의 안 보임, 2~5=희미하게 구분, 5+=확실히 구분). 특히 "레벨/위계"를 나타내는 토큰(elevation, 명도 스케일)은 위계 순서대로 ΔE가 커지는지 확인 — 중간 단계보다 양 끝단이 더 가까우면 위계가 깨진 것.
- [ ] **Hue 계열 일관성**: 같은 "가족"으로 묶이는 토큰들의 OKLCH hue가 일정 범위 안에 있는가? 의도적으로 다른 그룹(예: 액센트만 약간 다른 hue)이 있다면 우연이 아니라 명시적 원칙으로 문서화한다.
- [ ] **인접 시스템과의 정합성**: 이 토큰이 다른 이미 확정된 토큰(예: Shadow 틴트가 브랜드 색을 재사용하는지)과 색 계열이 맞는지 확인. 별도로 새로 발명하지 말고 이미 검증된 값을 재사용할 수 있는지 먼저 확인.
- [ ] **범위 밖 항목 존재 확인**: 이번에 다루는 토큰과 세트로 묶이는데 아직 안 건드린 게 있는가? (예: 브랜드색 바꾸면서 상태색/다크모드를 깜빡하는 경우) — 있다면 "후속 과제"로 명시적으로 남긴다.

## B. 화이트보드/시각 비교 단계

- [ ] 순수 색상/값 블록과, 이름·수치를 담은 중성 배경 라벨을 **분리**해서 배치한다(색 위에 텍스트를 얹지 않는다 — 어떤 색이든 라벨은 항상 읽혀야 함).
- [ ] 화이트보드 도구(wired-\* 컴포넌트)는 "손그림 스케치" 스타일이 태생적 한계이므로, 최종 비주얼 품질 판단 근거로 쓰지 않는다 — 내용/조합 비교 용도로만 사용.
- [ ] 사용자가 직접 도형을 삭제해야 할 수 있음(에이전트에게 삭제 툴이 없음) — 재배치 필요 시 먼저 안내.

## C. OpenPencil(Figma 반영) 빌드 단계

- [ ] **HTML 임포트보다 Plugin API 직접 생성을 우선한다.** 단순한 사각형 1~2개면 HTML 임포트도 되지만, 요소가 여러 개(텍스트 포함) 얽히면 HTML→fig 변환 파이프라인이 절대좌표조차 깨뜨리는 걸 확인함. `figma.createRectangle()`/`figma.createText()`를 `eval`로 직접 호출하는 방식이 훨씬 안정적.
- [ ] **폰트명에 따옴표를 쓰지 않는다.** `font-family: Pretendard`(O) / `font-family: 'Pretendard'`(X, 따옴표까지 폰트명으로 인식해 조용히 실패).
- [ ] **텍스트 노드는 `textAutoResize = 'WIDTH_AND_HEIGHT'`를 명시한다.** 안 하면 긴 텍스트가 예상 밖으로 줄바꿈되어 다음 요소와 겹칠 수 있음.
- [ ] **여러 블록을 쌓을 땐 절대좌표(x/y)로 명시한다.** `margin-top` 등 문서 흐름에 의존한 배치는 겹침을 유발할 수 있음(HTML 임포트 경로에서 특히).
- [ ] **폰트가 실제로 이 서버에 설치돼 있는지 `fc-list`로 먼저 확인한다.** 설치 안 된 폰트를 지정하면 조용히 다른 폰트로 대체되어 렌더링됨 — 에러 없이 실패하므로 반드시 사전 확인.
- [ ] **`eval` 코드를 파일로 전달할 땐 `<` 리다이렉션이 아니라 `cat file | ... --stdin` 파이프를 쓴다.** (`<` 리다이렉션에서 stdin 인식 실패 확인됨)
- [ ] **`.fig`를 만들 때 최소 blank HTML을 먼저 import해서 베이스 파일을 만든 뒤 `eval -w`로 채운다** (FILE 인자 없이 `eval`을 실행하면 실행 중인 GUI 앱에 연결을 시도하다 실패함 — headless 환경에선 항상 FILE 인자 필요).
- [ ] **페이지 전체를 덮는 배경 사각형을 항상 명시적으로 먼저 그린다.** 자유 텍스트 노드만 여러 개 흩어놓으면 export 시 바운드 계산이 가장 오른쪽/아래 텍스트를 놓쳐서 잘릴 수 있음(실제로 겪음) — 배경 사각형이 있으면 전체 캔버스 크기가 확실히 바운드에 포함됨.
- [ ] **`figma.createFrame()`으로 만든 프레임에 자식을 `appendChild`할 때, 자식 좌표가 프레임 기준 상대좌표로 자동 변환되지 않고 겹쳐버리는 버그가 있음(2026-08-22 확인).** 여러 섹션을 나란히 배치해야 할 땐 실제 FRAME 노드 대신, 페이지에 직접 배치하되 섹션별로 X/Y 오프셋을 좌표 계산에 직접 더하는 방식(헬퍼 함수가 `{offsetX, offsetY}`를 들고 다니는 패턴)을 쓴다.

## D. 렌더링 후 검증 (사람이 반드시 봐야 하는 것)

숫자로 검증 가능한 항목(A)을 다 통과해도, 아래는 **반드시 렌더링된 이미지를 실제로 보고** 판단해야 합니다 — 코드가 "정상"이라고 보고해도 그림이 깨질 수 있음을 이 세션에서 반복 확인함.

- [ ] 텍스트가 잘리거나 겹치지 않았는가 (특히 제목처럼 폰트 크기가 큰 텍스트)
- [ ] 한글/특수문자가 올바른 폰트로 렌더링됐는가(다른 폰트로 조용히 대체되지 않았는가)
- [ ] 색이 의도한 위치에 정확히 칠해졌는가
- [ ] 전체 구도가 "가을 소나기" 같은 의도한 감정/톤을 실제로 주는가 — 수치 통과와 미적 완성도는 별개임
- [ ] 요소 개수가 늘어날수록(카드+버튼+텍스트 등 실제 조합) 별도로 다시 확인 — 단순 스와치에서 통과했다고 복잡한 조합에서도 안전하다고 가정하지 않는다
